# Provider unlink WIP: isolated, non-production experiment

Based on yeogibwa-account-login-20261111 at 6170c2d652244f9e213c52139ad19447065365e5. Only the adapter, its synthetic tests and this file are added. No routes, UI, guard, owner-auth, owner-stores, environment, provider apps or live data are changed. This is NOT end-to-end withdrawal or working recovery.

## Official contracts checked 2026-11-12 KST
- Kakao: https://developers.kakao.com/docs/latest/en/kakaologin/rest-api#unlink . POST https://kapi.kakao.com/v1/user/unlink with Bearer access token. Success returns unlinked service user ID. Strict numeric ID equality (including 64-bit IDs without rounding) is required; mismatches/errors stay pending. No admin key path.
- Naver: https://developers.naver.com/docs/login/api/api.md (sections 3.3, 4.4), https://developers.naver.com/docs/login/devguide/devguide.md . Current endpoint is POST https://nid.naver.com/oauth2.0/revoke with client_id, client_secret, token, token_type_hint=access_token in form body. HTTP 200 also means already revoked OR nonexistent token, without a distinguishing body. Therefore ALL Naver responses remain pending here; the adapter does not invent stronger confirmation or use the legacy delete-token API. No automatic 503 retry.
- Google: https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke . POST https://oauth2.googleapis.com/revoke with form-body token. Documented HTTP 200 confirms processing; 400/errors remain pending, never inferred as already complete. Only empty or {} bodies are accepted conservatively. Revoking an access token also revokes its corresponding refresh token; Google documents project-wide scope across clients. This does not prove propagation or local deletion.

## Caller contract, not an authentication implementation
Call createProviderUnlinkAdapter({experimental:true, fetchImpl, now, timeoutMs}) to obtain unlink(input). There is no default transport and no app integration. Tests inject fake fetch ONLY. Do not connect real customers or production. A later integration needs separate review/authorization.

input.expected is the trusted stored link tuple {provider, clientId, subject}. input.reauthenticated must contain the EXACT same tuple plus authenticatedAt (integer epoch milliseconds), tokenBound:true and freshAuthentication:true. input.accessToken is a NEW access token from fresh interactive reauthentication, not an ID token, refreshed background token or stored historical token. Naver additionally needs in-memory clientSecret. Reauth must be no older than five minutes; future timestamps are rejected. Five minutes is local safety policy, not a provider guarantee.

The caller MUST verify state/CSRF, nonce/PKCE where applicable, issuer/audience/client, token validity and identity from provider-verified evidence, bind the SAME supplied token to the SAME stored provider/client/subject, and bind a single-use reauth challenge to the currently authenticated owner, session, operation and intent. Never match by email, nickname, coercion or merely successful login; a different account must fail closed. Google sub/aud/issuer and Kakao app ID versus OAuth client ID need correctly verified mapping; Naver profile ID must come from the same token exchanged under the expected client. Boolean assertions are a trusted-server contract, NOT proof, and must never come directly from a browser. No such flow is implemented here. Prevent replay/concurrent operations outside this adapter.

Tokens/secrets exist only in call-local memory and the necessary HTTPS request. The adapter never persists, logs, returns, hashes or includes them in errors; results contain only fixed status/reason/automaticRetry fields. Caller/transport/APM must disable request, header and body logging and discard references after use. JavaScript GC does not promise secure memory zeroization. No tokens in URLs or persisted for retries.

Transport: three literal HTTPS endpoints, POST only, redirect:error, credentials:omit, no-store and no-referrer. No endpoint override. Timeout 50..3000 ms (default 3000) covers headers AND body, with abort plus a result deadline even for an uncooperative fake transport. Response cap 4096 bytes (declared and streamed), request cap 8192 bytes, token cap 2048 characters. Transport must honor abort, never secretly retry/redirect, and never log. Response URL/redirect status is checked. Oversized, malformed, unknown, non-200, timeout and transport errors return pending after dispatch. No automatic retries on any outcome. Contract failure is blocked before dispatch. Conservative body/ID limits can leave legitimate results pending.

## Remote-success/local-commit crash race: NOT solved
The provider may revoke successfully before timeout, connection loss or process crash, or between a success result and durable local commit. pending is NOT failure and NOT permission to retry. A future integration must persist a secret-free operation intent and serialize owner/link mutations BEFORE dispatch, then atomically commit the confirmed local lifecycle result. A crash after remote success still requires reviewed reconciliation; already-revoked/invalid responses cannot reconstruct proof, and new login may recreate consent. Do not mark withdrawal complete, delete stores, revoke local sessions or silently retry based on this adapter alone. Outbox/reconciliation, durable receipts, deletion policy, session invalidation and user recovery are UNIMPLEMENTED.
